## CPU use (investigated 2026-11-17)
Installer 1.0.5 tested OK, but the owner saw ~8 % CPU (= one full core of 12) while the app sat in the tray.
Findings (measured with Get-Process TotalProcessorTime + a TEMP frame logger, see below):
- **Tray: FIXED (2026-11-17, work PC).** Cause: hiding used `ViewportCommand::Visible(false)` (= SW_HIDE); Windows never sends WM_PAINT to a hidden window, so eframe's redraw request was never answered, its winit loop spun a core and `update()` stopped (cloud sync in the tray stalled). Now "in the tray" = a minimized tool window: `window::hide_to_tray` (SW_HIDE, `WS_EX_TOOLWINDOW` on / `WS_EX_APPWINDOW` off so no taskbar button or Alt+Tab entry, then `SetWindowPlacement` with `WPF_SETMINPOSITION` at -32000,-32000 + SW_SHOWMINNOACTIVE: a minimized tool window otherwise sits at the bottom-left of the screen as a small caption stub, visible with an auto-hide taskbar) and `window::restore_from_tray` (SW_HIDE, styles back, SW_RESTORE, SetForegroundWindow). Used in `FeatherApp::hide_to_tray`, `show_window` and the `--minimized` `rehide_frames` path; if the window gets un-minimized from outside while `hidden` (a second launch's FindWindow + SW_RESTORE nudge), `update` calls `show_window`. Measured: 0.0-0.3 % of one core in the tray (both `--minimized` and X with close_to_tray), `update` keeps running, a second launch restores it at its old size with the taskbar button back. Tested with a throwaway `USERPROFILE` (+ `FEATHER_LIBMPV`) so the real settings stay untouched. Not tested yet: the tray icon's Open/Quit menu and restoring a maximised window.
- **Window visible + idle:** ~10 frames/s, ~7 % of one core (~0.6 % in Task Manager). Every such frame has no input events and only the app's 3 s / 5 s timers as repaint causes; mpv's update callback is 0 and the scanner is idle, so the wakeups come from window events inside eframe/winit that the app never sees. Not found yet. Ideas: make frames cheaper (e.g. `lib.filtered()` over ~760 clips runs every frame), find the winit event source.
- **TEMP debug code to remove when done:** `FP_DEBUG_FRAMES=1` block at the top of `FeatherApp::update` (writes `target\frames_debug.txt`: frames/s, input events, repaint causes) and `mpv::UPDATE_CALLS` counter in `on_update`.

## Architecture decisions (keep unless there is a good reason)
- **GUI:** eframe/egui 0.33 with the **glow** (OpenGL) renderer. Needs Rust 1.88+.
- **mpv:** `src/mpv.rs` loads libmpv at runtime with `libloading` (no import library, no linking setup). It uses the **OpenGL render API**, not a child window (`wid`), so egui popups and menus can draw over the video (no airspace problem).
- **Video drawing:** mpv can only render at the origin of a framebuffer, so it renders into an off-screen texture/FBO sized to the video rectangle, then that is blitted into the egui paint-callback rectangle (`VideoGl` in `player/video_gl.rs`). mpv's update callback calls `egui::Context::request_repaint`.
- **Opening a clip:** `Player::open_clip` sets mpv's `start` option ("50%" / trim "%") before `loadfile` when the start is known up front (trim start, or Middle with the duration from prefs `durations`), so mpv opens at that spot instead of decoding from 0 and exact-seeking after load (that double decode made clips load slowly). `start` is set on every open ("none" otherwise) since it is a global option. Unknown duration: the old seek-after-load path. Lua scripts/ytdl are off (`?`-prefixed = optional init options).
- **Never block the UI thread on mpv** (measured 2026-11-17, click -> first frame went from ~1.5 s to ~150 ms): the UI thread is also mpv's render thread, and libmpv's VO waits up to 200 ms for each frame to be rendered (`mpv_render_context_render() not being called or stuck` in the mpv log). So: `Core::cmd`/`Core::set` are always async (`mpv_command_async` / `mpv_set_property_async`, carried out in order); `Player::poll` makes no blocking reads, `time-pos`/`duration`/`pause`/`eof-reached`/`track-list` are observed (`Core::observe`, PROPERTY_CHANGE events; mpv only reports changes, so values are kept across files); players that aren't on screen (preloading standby, the open one while loading) are rendered off-screen every frame when mpv has a frame (`render_offscreen`, `frame.gl()` in `update`).
- **Audio mix before opening:** the old clip is `stop`ped first, and when the clip's audio track layout is known, `lavfi-complex`/`aid` are set before `loadfile` (`open_clip` `preset`), so nothing is rebuilt + re-seeked after it starts (that was the 600-900 ms lag with default tracks 2-5). Layouts come from the scanner (`scanner::audio_tracks`, ffprobe, queued with thumbnails) and from mpv, saved in `<data>\rs_audio_tracks.json` (Rust only). "Middle" starts open on the keyframe (`hr-seek=no` until the first PLAYBACK_RESTART): these clips have a keyframe only every ~4.2 s. Debugging: `FP_DEBUG_LOAD=1` writes load timings to `target\load_debug.txt`, `FP_MPV_OPTS="log-file=...,msg-level=all=v"` adds mpv options.
- **Clips open paused** and start once their audio tracks are handled (`Player::autoplay`, 1.5 s safety net), like Python `_mpv_hold_for_mix`: with default tracks 2-5 the lavfi mix + seek-back after load made the picture jump back ~100 ms after it started.
- **Preload:** a second `Player` (`FeatherApp::standby`) opens the clip card hovered for 120 ms (`ClipGrid::hovered`), paused at its start point, tracks applied on a clone of `AudioTracks`. Clicking that clip (same `Start`) swaps the two players (`std::mem::swap`); the old one is stopped (unloads). `release_preload` before deletes / `ReleaseFile` / hide to tray, since mpv locks the file. Both players are shut down in `on_exit`.
- **Resize:** while the video rect keeps changing size, `VideoGl` keeps its texture and mpv renders at the old size, blitted scaled evenly and centred (LINEAR, keeps the aspect ratio); after `RESIZE_SETTLE` (150 ms) without change it reallocates at the real size (player_view requests a repaint then, also when paused). Re-allocating + mpv rebuilding its scaler buffers every frame made window resizing lag.
- **Shutdown order matters:** free the render context (GL thread, context current), then `mpv_terminate_destroy`. This is done in `on_exit`.
- **Seek bar:** the Python `TrimSlider` behaviour: pressing pauses and seeks live while dragging (every >= 2/10000), release seeks and resumes. A short hold after seeking stops the position poll from snapping the thumb back.
- **Audio tracks:** same rules as FeatherPlayer `_at_build_graph`. One untouched track is picked with `aid`; otherwise a `lavfi-complex` graph is built (`[aidN]volume=V[vK]`, then `amix=inputs=N:duration=longest,volume=N[ao]`, since amix divides the level by N). Set `lavfi-complex` only when it changes (each set rebuilds mpv's filter graph). After applying, seek back to the old position (`absolute+exact`), because adding a track makes playback jump ahead.
- `libmpv-2.dll` is NOT in the repo (`.gitignore` excludes dlls/exes). It is found in `%USERPROFILE%\FeatherPlayer\libmpv-2.dll`, the same place the Python app uses.
